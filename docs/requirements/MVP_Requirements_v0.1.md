## 1. 目的・背景

### 1.1 目的

機種、開発案件、管理要否、イベント要否・計画・開催状況、機種開発マイルストーン、エビデンス、成果物を**一つのExcelブック**で統合管理する。管理担当者が効率よく入力・更新でき、閲覧ユーザーがガントチャートや直近イベント一覧を使って開発状況を確認できることを目指す。

### 1.2 基本方針

1. **データとUIを論理的に分離する**。管理画面は作業効率、閲覧画面は一覧性・可読性を重視する。
2. **開発案件（機種×開発案件）を主要な管理単位**とする。把握した案件は管理対象外でも登録する。
3. **開催回ごとのデータ保存と、案件×ステージ単位の表示集約を区別**する。
4. **情報種別ごとに正本を定義**し、Excelに集約する。すべての情報の正本をExcelとみなさない。
5. 将来Qlik Senseで使えるよう、構造化データをIDで関連付ける。ただし**MVPでは実連携を行わない**。

## 2. スコープ

### 2.1 MVPに含める

- 開発案件（管理対象外も含む）、管理要否、イベント種別ごとの適用要否を管理する。
- イベント開催回、計画日・実績日・開催状況、開発日程マイルストーンを管理する。
- エビデンス・成果物の外部参照情報を独立一覧で管理する。
- 管理画面で一覧編集＋詳細編集、要対応情報の抽出を可能にする。
- 4仕様のガントチャート、今後2か月＋過去未開催イベントのリストを閲覧できる。
- 単一Excel原本を共有場所に保管し、管理担当者の更新と閲覧者の参照を運用する。

### 2.2 MVPに含めない

| 項目 | 区分 | 根拠 |
|---|---|---|
| 外部システムからの自動取込・自動同期 | Not Now | 原Q15、補完Q2 |
| 自動通知・対応依頼ワークフロー | Not Now | 原Q15、補完Q3 |
| Qlik Senseへの実接続・アプリ作成 | 別フェーズ | 原Q14/Q15 |
| 開催後の指摘対応・成果物承認の進捗管理 | Later | 補完Q1 |
| 組織横断の承認制度そのものの変更 | Not Now | 原GrillMe Scope |
| 全機種・全案件の本番初期登録 | Not Now | 原GrillMe Scope |

### 2.3 後続設計で決める項目

シート・列の物理配置、関数・条件付き書式・VBA・Power Queryの選択、画面レイアウト・配色・記号、ガントの固定列数・具体的なスライド操作、計画変更履歴の詳細、リンク切れ点検方式、ステータスの例外遷移等は **Later**。本書の記載から自動的に実装方式を確定しない。

## 4. 概念データ要件

### 4.1 論理データ構造（要件レベル）

```text
機種
 └─ 開発案件（機種×開発案件）
     ├─ 管理要否
     ├─ 開発マイルストーン［0..複数］
     ├─ イベント適用要否［イベント種別ごと］
     └─ イベント開催回［0..複数］
         ├─ イベント種別
         ├─ ステージ（表示集約用）
         ├─ 計画日／実績日／開催状態
         └─ エビデンス・成果物［0..複数］

エビデンス・成果物一覧：資料単位の独立した参照情報を保持し、関連対象を識別する
情報種別別正本対応表：情報種別とその正式情報源・提供元・確認方法を対応付ける［内容TBD］
```

上記は**論理関係の説明**であり、Excelシート数・テーブル数・物理キーの形式、資料との中間テーブル設計までを決めるものではない。特にステージの紐付け先、複数の関連対象を持つ資料の表現方法は後続設計事項である。

### 5.1 代表業務シナリオ（受入テストへ展開する案）

1. **新規案件**：案件登録 → 管理要否を設定 → イベント種別ごとの適用要否を設定。
2. **イベント計画**：対象となるイベントの開催回を登録 → 計画日を設定 → 計画済として確認。
3. **変更・再開催**：計画変更は同じ開催回を更新／再開催は別開催回を追加 → 対応する表示を確認。
4. **開催・資料登録**：開催日（実績）・開催済ステータスを更新 → 証跡・成果物リンクを追加。
5. **日常点検**：未判定・未計画・予定日超過・未開催・更新確認対象を抽出し、元情報を確認して更新。

この手順は**要件を具体化するためのシナリオ案**であり、詳細な操作順・操作回数・更新UI部品は未確定。

### 9.1 MVP受入の判定方法（提案・未承認）

1. 各ACにテストデータ、前提条件、操作手順、期待出力、Pass/Fail判定者、証跡保存先を設定する。
2. 「機能動作」だけでなく、誤った関連付け・表示欠落・不正な編集を検出するケースも検討する。
3. 受入不能な重要欠陥の扱い、合否しきい値、速度等の定量評価は、実環境確認後に定義する。
4. AC-09、AC-10等のブロック要因が解消するまで、MVP全体の受入を完了と判定しない。
