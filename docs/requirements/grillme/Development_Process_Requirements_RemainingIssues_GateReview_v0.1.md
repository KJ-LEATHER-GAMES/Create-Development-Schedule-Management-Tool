### 1.2 残課題補完GrillMe（Q1–Q6）

### 1.3 特に重要な整合ルール

1. **イベントの「開催済」は必ずしも成果物・指摘対応の完了を意味しない。** Q11の「過去の未完了」は、当面、予定日を過ぎた未開催イベントとして扱う。指摘対応残件の追跡はLater。
2. **イベント開催回の保存粒度と、ガント上の行の表示粒度は別。** 保存は開催回、表示は原則「案件×ステージ」に集約。重複は件数・詳細一覧で確認する。
3. **Excelに表示されるデータがすべてExcel正本とは限らない。** 正本マッピングは情報種別別に定義する。
4. **『変更発生時更新』は外部システムからの自動同期を意味しない。** 管理者が変更を把握した後に手動更新する。

## 3. 受入基準候補（正式要件定義に落とし込むためのドラフト）

> ここに列挙するのはQ6-Bの選択から導く検証案であり、すべてがユーザー承認済みの正式受入基準という意味ではない。

| ID | 検証シナリオ | 観察可能な期待結果（案） |
|---|---|---|
| AC-01 | 2件の開発案件を登録し、1件を管理対象外とする | 案件が区別され、管理要否ごとに抽出できる |
| AC-02 | 対象／対象外／未判定のイベント適用要否を案件別に設定する | それぞれの状態が保持・区別される |
| AC-03 | 同じ案件・イベント種別に初回と再開催を登録する | 2つの開催回が失われず個別に参照できる |
| AC-04 | 計画日変更、開催済更新、中止を登録する | 日付・ステータスの更新が該当レコードのみに反映される |
| AC-05 | 1開催回に2つの資料リンクを登録する | 両資料をイベントから参照でき、別案件と混同しない |

| AC-07 | 4仕様のガントで同一案件のデータを表示する | 表示粒度・行粒度が指定どおりで、表示期間のスライドで対象を切り替えられる |

| AC-10 | 管理者が更新し、閲覧ユーザーがアクセスする | 閲覧ユーザーの誤編集を防ぎ、更新後の情報を確認できる（実環境確認が必要） |

## 4. 未決事項

### Now — 正式要件定義の確定または残るExitを満たすために必要

1. **情報種別別の正本対応表**（情報名、正本、提供元、入力方法、管理担当、確認方法、証跡要否）と具体的な定期確認周期（EXIT-03）。
2. **直近2か月リストの時間境界・状態条件**（当日を含めるか、暦月か応当日か、過去の未開催に未計画・中止を含めるか）（EXIT-05）。
3. **実運用環境・規模**（Excelバージョン、デスクトップ／Web、保存先、案件・イベントの概数、閲覧人数、同時利用、バックアップ／ロールバック方針）（EXIT-06）。
4. **検証仕様の具体化**（ケースごとの準備データ、期待出力、合否条件、環境・性能の受入水準）（EXIT-07）。

### Later — 詳細要件・基本／詳細設計

- ステータス遷移の例外規則、再計画履歴、更新日時などの詳細項目定義。
- ガントの表示列数・色・記号、重複セルの描画、単一機種画面の具体レイアウト。
- Excelシート・関数・VBA・Power Query等の実装選定。
- エビデンスURLのリンク切れ点検方式、指摘対応や成果物承認状況の別管理。
- Qlik Senseへの接続方式・抽出形式・更新方式の実装設計。

### Not Now — 意図的に判断しない

- 外部システム自動取込、通知、Qlik SenseアプリのMVP実装。
- 組織横断の承認プロセスの変更。
- 全機種・全案件の本番データ登録。

### Scope外として退避

| 論点 | 扱い |
|---|---|
| 数式、VBA、画面レイアウトなどの実装詳細 | Later |
| Qlik Senseの実連携とアプリ開発 | 別フェーズ／別GrillMe候補 |
| 組織の承認ルールそのものの変更 | Not Now |

## 5. Question Limit到達時の取扱い

- 追加質問の要否：**Exit全達を目指すなら必要**。ただし追加のA/B/C質問だけでなく、客観的な事実確認・要件書ドラフトによって解消できる項目が多い。
- 目安：新たなGrillMe質問は**2問程度**（正本／期間境界など、実際に選択が必要な論点）、別途環境の事実確認と受入テストドラフトのレビューを行う。ユーザーの事前承認なしに追加しない。
- 選択肢：①追加質問を承認／②未決を明示して正式要件定義書v0.1のドラフトへ進む／③別GrillMeや別の確認工程に分離。
