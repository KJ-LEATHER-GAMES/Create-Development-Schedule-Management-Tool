## 1. GrillMe基本情報

### GrillMe名称
開発プロセス統合管理ブック 要件定義 GrillMe（MVP対象）

### Objective
単一Excelブックを中心に、開発プロセス関連情報を整合的に管理・表示する仕組みについて、**MVPの業務要件・情報要件・画面要件・運用要件・受入基準**を確定する。将来のQlik Sense連携を妨げないデータ構造上の制約も要件として定める。

### ユーザー提示済み条件（確認済み入力）
- 一つのExcelファイルで、機種一覧、管理有無、イベント有無、イベント計画、進捗、機種開発日程、各情報のエビデンス、イベント成果物を扱いたい。
- ユーザー向けダッシュボードとして、**日単位のガントチャート**、**月の上旬・中旬・下旬単位のガントチャート**、**直近2か月のイベントリスト**を想定。
- **管理画面と閲覧用画面を明確に分離**し、管理側は操作性を優先したい。
- 将来的なQlik Senseへの拡張を想定する。

### Scope（今回のGrillMeで決定すること）
1. 管理対象・識別単位・情報の関係（機種、案件、イベント、計画、成果物、証跡）。
2. 管理有無／イベント有無／進捗／日程の業務上の定義、状態遷移、欠損・対象外の扱い。
3. 管理者と閲覧者の利用目的、主要操作、入力・更新フロー、更新責任。
4. 表示要件（ガント2粒度、直近2か月リスト、絞り込み、表示対象と読み取り方）。
5. エビデンス・成果物の参照と更新履歴に関する要求レベル。
6. MVP範囲、Excel運用上の主要制約、将来のQlik Senseを見据えたデータ可搬性、受入基準。

### Out of Scope（今回決定しないこと）
- Excelシート名、列の物理配置、関数、VBA、Power Query等の実装選定・作成。
- ガントチャートの具体的なセル幅・色・詳細レイアウト、画面モックの完成。
- Qlik Senseアプリ構築、データロードスクリプト、配布設定。
- 全イベント種別・全機種・全証跡ファイルの実データ登録。
- 組織横断での承認制度・業務ルール自体の変更。

**Scope Rule**：重要な範囲外論点は `Later` / `Not Now` / `別GrillMe候補` に退避し、勝手に取り込まない。Scope拡張はユーザー承認が必要。

## 2. Exit Criteria

| ID | 終了条件 | 初期Status |
|---|---|---|
| EXIT-01 | 管理対象、基準となる識別単位、主要データ間の関係を説明できる | Not Met |
| EXIT-02 | 管理有無・イベント要否・イベント実施状況・進捗・日程の意味と代表的な状態を区別できる | Not Met |
| EXIT-03 | 各情報の正本・更新責任・入力方法・更新頻度・証跡参照の原則が決まっている | Not Met |
| EXIT-04 | 管理画面と閲覧画面の役割、管理側の主要業務シナリオと操作上の重点が決まっている | Not Met |
| EXIT-05 | 日単位／上中下旬単位ガント、直近2か月リストについて、表示対象と基本操作・集計解釈が決まっている | Not Met |
| EXIT-06 | MVPとLaterの境界、将来Qlik Sense連携を考慮したデータ保持要件、主要運用制約が決まっている | Not Met |
| EXIT-07 | 業務要件を検証できる受入基準と、正式要件定義書への反映事項が整理されている | Not Met |

**Exit Rule**：全項目がMetなら質問が残っていても終了提案し、最後の終了判断はユーザーが行う。

## 3. Question Limit

- **最大15問**（A/B/C等から正式な意思決定を求める質問だけをカウント）
- 用語確認・補足説明・推奨理由への確認・事実確認はカウントしない。
- 15問到達時にExit未達なら自動延長せず、未達と理由を示し、追加・保留・別GrillMeのいずれかをユーザーが決める。
- 目標は15問消化ではなく、必要十分な決定で停止すること。

## 4. 質問の優先順位と動的計画

優先基準：**意思決定への影響度 → 不確実性 → 後続判断への依存関係 → 今決める必要性**。

以下は**質問候補**であり、回答に応じて統合・削除・順序変更する。固定の15問ではない。

| 優先 | 質問候補（意思決定テーマ） | 対応Exit |
|---|---|---|
| P0 | 基本管理単位・一意キー（機種、開発案件、イベント） | 01 |
| P0 | 管理対象へ含める条件と適用／非適用の判定 | 01,02 |
| P0 | 管理有無・イベント有無・未判定・不要・未計画の区別 | 02 |
| P0 | イベント種類、同一対象での繰り返しや再計画の扱い | 01,02 |
| P0 | 計画日・実績日・機種開発日程・進捗・遅延の定義 | 02 |
| P0 | 入力の正本・証跡・成果物の紐づけ | 03 |
| P1 | 管理者の主要更新シナリオ（一括更新／個別更新） | 04 |
| P1 | 更新担当・レビュー者・更新頻度・複数人運用 | 03,04 |
| P1 | 閲覧者の対象範囲と主要な判断場面 | 04,05 |
| P1 | ガント2表示の対象・期間・絞り込み・重複イベント表現 | 05 |
| P1 | 直近2か月リストの期間・表示基準・状態フィルタ | 05 |
| P1 | MVPに不可欠なデータ・機能と後回しにする機能 | 06 |
| P1 | Excel運用条件（データ量、性能、保存・同時利用、利用環境） | 06 |
| P2 | Qlik Sense移行に必要なデータ抽出・識別子・定義一貫性 | 06 |
| P2 | 実業務シナリオに基づく受入基準・終了可否 | 07 |

**設計上の仮説（未確定）**：一枚の表に全データを押し込まず、機種／開発案件／イベント／日程／証跡・成果物などの管理情報を論理的に分け、画面は参照先として扱うと、更新ミス削減とQlik Sense展開に有利。ただしシート構成や実装方法は本GrillMeで確定しない。

## 5. 標準質問フォーマットと運用

毎回、**GrillMe Qn / 15** の見出し、1つの判断論点、原則A/B/Cの3択、**推奨案を1つ**、判断軸・短い理由、回答依頼を提示する。4択は必要なときだけ許可する。

1. ユーザー回答を受け、`Qnは「B：…」で確定` という形式で簡潔に確定内容を記録する。
2. `推奨案で` は直前の推奨記号として正規化し、再確認しない。
3. 選択肢外なら意図を保持して選択肢を再構成し、無理に当てはめない。
4. 新たな論点は `Now` / `Later` / `Not Now` に分類する。Scope外論点は別途退避する。
5. 重大Decisionはユーザー確定時点でDecision Logへの正式記録候補にできる。GrillMe終了は必須条件ではない。

## 6. 初回の正式質問（未回答）

### GrillMe Q1 / 15：基本の管理単位

**質問**：管理台帳で「1件」として一意に識別する基準を、どこに置きますか？ これは、機種一覧とイベント・日程・証跡の結び方を左右します。

- **A. 機種単位**：基本的に1機種につき1つの管理レコードとする。単純だが、同一機種の複数案件・複数期間の区別に工夫が必要。
- **B. 機種 × 開発案件単位［推奨］**：機種に紐づく開発案件を親レコードとして管理し、イベント・日程・エビデンスは複数紐づけられる前提とする。
- **C. 機種 × イベント単位**：イベントごとのレコードを基本にする。イベント追跡は行いやすい一方、機種単位情報が重複しやすい。

**推奨：B**。判断軸は**情報の整合性／変更への耐性／将来のQlik Sense拡張**。ただし実際に「開発案件」が機種から独立した概念でない場合にはAへの修正が妥当。

**回答方法**：`A / B / C` または独自案を文章で回答。

## 7. 未決事項トラッキング（初期）

### Now
- Q1：基本管理単位（未確定）

## 8. GrillMe終了時サマリーの出力仕様

以下を必ず提示する。

1. **確定事項**：Q番号と結論だけを簡潔に記載
2. **未決事項**：Now / Later / Not Now
3. **Scope外退避事項**：分類先と理由
4. **Exit Criteria判定**：EXIT-01〜07のMet / Not Met
5. **追加質問の要否**：必要なら理由と提案数
6. **正式ドキュメントへの反映対象**：MVP要件定義書（業務・情報・画面・運用・非機能・受入基準）とDecision Log
7. **Next Actionを1つ**＋Done When

### 想定の正式成果物（GrillMe終了後に作成）
- `MVP_Requirements_v0.1.md`：要件ID、優先度、説明、受入基準、根拠、未決事項
- `Decision_Log.md`：判断理由、代替案、影響範囲、変更履歴

**終了判定の原則**：質問数を満たすための質問を追加しない。ユーザーがExitを確認し、最終承認したとき終了する。
