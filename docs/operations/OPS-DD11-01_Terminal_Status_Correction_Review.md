## 1. 目的・問題の所在

開催回が実際には開催していないのに`開催済`と登録された、または中止ではないのに`中止`と確定された場合、通常UIから`開催予定`等への逆遷移はできない。一方、**開催状態の正本は`tblOccurrence.OccurrenceStatus`だけ**であり、`tblOccurrenceStatusHistory`はDD11-01 Bで不採用。`StatusReason`等は現在状態の根拠で、過去の状態監査履歴ではない。

**OPS11-01の判断対象は「終端状態誤登録時の例外運用」だけ。** 日付のみの事実誤記訂正は既決の`tblDateHistory`追記操作で扱い、開催回の新設で誤登録を隠さない。通常の編集権限拡大、新規承認ワークフロー、監査専用の業務テーブル、追加定期バックアップを採用しない。

## 2. 変更しない不変条件

1. `OccurrenceID`、`OccurrenceNo`、親`ProjectEventID`は維持。既存開催回を削除・再作成して訂正履歴を偽装しない。
2. `開催済`・`中止`からの**通常業務画面の逆遷移は禁止**。例外運用を通常操作へ開放しない。
3. `tblDateHistory`の正常確定行は**削除・上書き禁止**。日付の事実誤記があれば既決の変更種別に従い新`HistoryID`で訂正する。日付訂正だけで開催状態を変えない。
4. `tblEvidence`、`tblReconciliation`、`tblReconciliationReview`の既存の参照整合・追記専用規則を維持。証跡・差異レビューを隠蔽・削除しない。
5. **正本テーブルを直接セル書換えしない**。DD14の単一書込者・OperationKey・版照合・発番高水位、DD15の異常停止・全件照合をバイパスしない。
6. 関連する開催回・イベント要約・G02〜G04・L01/L02・管理者抽出・公式情報との差異を再照合する。中止・開催済・非適用の表示規則はDD12-01 Aのまま。
7. 外部に記録された誤登録の申告・修正前後・根拠・担当者・復旧結果が**アプリ内状態履歴の代替監査根拠**である。ただし同等のDB監査を保証するとはしない。

## 3. 扱うケースと通常操作との境界

| 事象 | 状態の訂正 | 日付の扱い | 要求する対応 |
|---|---|---|---|
| 開催していないのに`開催済`で確定 | 終端からの例外訂正が必要（通常UIは禁止） | 誤った実績日付があれば**日付履歴に別の訂正/取消記録**が必要。採用ChangeTypeとDateClassは事実に照らして確認 | 外部開催通知・議事録等で実施有無を確認、旧状態を保全 |
| 中止していないのに`中止`で確定 | 終端からの例外訂正が必要（通常UIは禁止） | 既存予定日が正しければ履歴をむやみに変更しない | 公式日程・連絡の確認、関連表示を再評価 |
| 開催済/中止の表示名・日付だけ誤り | **状態は変更しない** | 根拠付き日付訂正は既決の追記専用操作 | OPSの終端訂正機能を使わない |
| 開催済／中止が業務事実どおり | 何もしない | 必要な変更なし | 不要な復元や上書きを実施しない |
| 過去版復元で事象を解消したい | **全ブック復元を原則標準としない** | 後続正常更新・高水位巻戻りリスクあり | DD15 R01〜R08の条件が全て揃わないなら停止継続 |

**未確定境界**：誤った`開催済`の後に元の予定日をどう表すかなど、実績日付と状態の整合の個別ルールは実データ・外部根拠をもとに判断する。自動的に「実績→予定」へ書き換えたり、古いHistory行を削除したりしない。

## 4. 代替案（OPS11-01の新規判断対象）

| 案 | 例外訂正の管理方法 | 長所 | リスク・条件 | 評価 |
|---|---|---|---|---|
| **A（推奨）** | **管理担当者限定の保守例外操作**を、通常UIとは独立した保守手順として設計。外部インシデント記録に根拠・旧値・新値・操作版・OperationKey等を保全し、DD14／DD15と**同一の保存・再読込・全体整合ゲート**を通す | 原本の他の正常更新を維持しやすく、状態監査専用表を増やさない | **保守例外の実装手段・権限制限・Excel Windows/Webでの成立は未選定・Not Tested**。直接セル編集は認めない |
| B | 安全性・ID高水位・後続更新の無損失を証明できる場合のみ**版履歴の全ブック復元**で対応し、不可なら停止・個別変更管理 | 保守例外操作の新しい実装面が少ない可能性 | 後続正常操作とID高水位の巻戻り、採番再使用のリスクが大きく、実用性未確認 |
| C | 運用上は終端状態を固定し、状態訂正は別途実装方式の変更管理が承認されるまで一律停止 | システムの変更が最少 | 修正不能な誤登録が発生すると管理資料の正確性と業務継続に支障 |

**A案の承認を求める範囲は運用上の統制・条件であり、保守機能の実装成立ではない。** 権限管理・操作ログの外部記録・同一コミットゲートを物理的に実現できない場合は、`Blocked`／更新停止とし、別途設計変更レビューへ戻す。新規承認WFや通常画面の例外ボタンは追加しない。

## 5. A案の運用手順（提案／未承認）

| Step | 担当・入力／証跡 | チェックと実施内容 | 出口条件 |
|---|---|---|---|
| OP11-R01 申告 | 誤りを発見した関係者→管理担当者 | 対象`ProjectID`／`ProjectEventID`／`OccurrenceID`・疑義の状態・検知日・公式情報の所在を既存障害記録へ起票 | 対象特定・受付番号取得 |
| OP11-R02 隔離 | 管理担当者 | 当該開催回関連の更新を停止し、他操作への影響を確認。不整合・保存結果不明ならDD15のR01〜R03に移管 | 原本版・OperationKey・影響範囲を保全 |
| OP11-R03 事実照合 | 管理担当者が業務責任者・公式資料を確認 | 議事録、開催通知、取消記録、証跡リンクと現行状態を突合。必要に応じて機種開発責任者の既存責務範囲で事実を確認（**新承認WFではない**） | 訂正前後・理由・業務事実を確認 |
| OP11-R04 影響分析 | 管理担当者 | 同開催回の日付履歴、証跡、差異、要約状態、他の開催回、G02〜G04・L01/L02・管理抽出への差分、後続保存操作を列挙 | 影響IDと期待変更行集合が確定 |
| OP11-R05 訂正判断 | 管理担当者 | A案の保守例外操作が**実装・権限検証済み**で、単一書込者・直列保存・事前検証・外部記録を確保できるときのみ開始。未成立時は**Blockedで停止** | 実施方式・旧値・新値・修正理由・根拠を記録 |
| OP11-R06 原本訂正 | 管理担当者（例外保守経路のみ） | `tblOccurrence.OccurrenceStatus`の**訂正対象だけ**を正規の保存処理を介して更新し、`StatusReason`／`StatusChangedBy`／`StatusChangedAt`／根拠参照を訂正後の現行事実に一致させる（修正前値は外部障害票で保全）。日付の補償記録が必要なら既決の`tblDateHistory`追記を**同一論理保存要求**として整合確定。旧セルの直接編集は禁止 | DD14のOperationKey・版・PK/FK/UQ・期待行集合・確定順・原本再読込検証をすべてPass |
| OP11-R07 再検証・表示 | 管理担当者 | DD15 R05〜R07に従い高水位・全体参照・後続更新・元版・表示一括再生成を検証。根拠と操作結果を外部障害票へ記録 | `SourceRevision`・`DisplayRevision`整合と表示条件の検査完了 |
| OP11-R08 再開判定 | 管理担当者 | DD15 R08の再開条件と外部記録の完備を照合。未解決のOperationKey、版不明、ID巻戻り、整合性不合格なら停止継続 | 全条件成立のときのみ管理担当者が記録を残して再開 |

**障害優先ルール**：保存失敗・部分保存・結果不明が発見されたら、OPSの状態訂正を先行させず**DD15の封鎖・R01〜R08**を適用する。保守手順の上書きで復旧したことにしない。

## 6. 外部インシデント記録の最小項目（案）

| 記録項目 | 目的・要件 |
|---|---|
| 受付ID、起票日時、申告者、担当者 | 後で誰が判断・修正したか追跡 |
| `ProjectID`／`ProjectEventID`／`OccurrenceID`／`OccurrenceNo` | 不変IDで案件・回次を一意に識別 |
| 修正前の状態・理由・関連日付、修正後の状態・理由・関連日付 | アプリ内に状態変更履歴表がないことによる欠落を外部で補う |
| 公式資料・開催通知・議事録のリンク、事実確認者 | 変更の正当性を追跡。外部資料の実体は社内ファイルサーバーに保持 |
| 影響レコード一覧、期待行集合、表示影響、未変更である他レコードの確認 | 誤って他案件／他開催回まで変更しない |
| 旧SourceRevision、新SourceRevision、OperationKey、発番高水位、保存照合結果 | 直列確定・二重再送禁止・ID非再利用の証跡 |
| 実施環境、実施日時、表示更新結果、再開判定と根拠 | 失敗時の停止判定・再現／監査 |

外部記録は既存の業務記録手段（社内ファイルサーバー上の障害記録等）を利用し、**新業務テーブル・新承認WFを必須化しない**。閲覧権限・保持期間・アクセス統制の物理設定は未確定、運用開始前の確認項目とする。

## 9. OPS11-01の判断依頼

- **A（推奨）**：管理担当者限定の例外保守経路・外部根拠・DD14/DD15の同一整合ゲートで誤登録を訂正。技術成立しなければBlockedを継続。
- **B**：厳格な条件付きの全ブック版履歴復元のみを採用。条件を満たさない場合は停止・変更管理。
- **C**：直接の訂正運用を採用せず、別設計変更の正式承認まで終端状態訂正を実施しない。

**OPS11-01は承認待ち。** いずれもDD11-01 Bを変更せず、通常UIでの逆遷移を許可せず、状態監査専用表を追加しない。承認後も実装・実機テストは別管理とする。
