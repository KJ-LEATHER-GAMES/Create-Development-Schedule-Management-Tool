## 0. 目的・対象・状態

- 要求IDから**設計決定・親テスト・詳細ケース・期待値・実施証跡**まで双方向に参照できる状態を作る。
- 実装前レビューで入力条件・操作順・期待結果・Pass判定根拠を確認し、後工程で結果を記入する。正常系を優先し、無制限の網羅的テストをMVPに追加しない。
- **継承する確定判断**：詳細設計Q01〜Q24、CONS-DD-01=A、DD10-01=A、DD11-01=B、DD12-01=A。**DD13-01=A（2026-11-16）**はこのテスト設計の採否にのみ追加した判断。**DD14-01=A（2026-11-16）**は論理的な採番・直列コミット方式の承認であり、**DD15-01=A（2026-11-17）**は障害復旧・表示鮮度の論理仕様承認である。いずれも既決事項やテスト実施結果を変更しない。**DD15-02 A（2026-11-17）**はC14/C15の採否統合のみを確定し、全41件をNot Testedで管理する。
- **運用上の限界**：Q23/Q24はテストのトレーサビリティとGate運用に関する判断。Q24のExit判定は試験Passとは別。基本設計EXIT-06=Not Met/未Freeze、詳細Exit=Not Evaluated、Excel実装=Not Started。
- **対象外**：Qlik Sense実接続、外部自動取込、新承認WF、定期別バックアップ、実機PoCの前倒し。技術成立性の確認は定義しても実施済みとはしない。

## 1. テスト実施ルール（DD13-01 Aでテスト設計として採用）

| 項目 | 記録ルール |
|---|---|
| 状態 | `Not Tested`（未実施）／`Pass`（合格）／`Fail`（不合格）／`Blocked`（環境・未決事項で実施不能）／`N/A`（当該環境で対象外、理由と承認が必要） |
| 合格条件 | 事前条件成立、記録された操作を実施、**全ての必須期待結果**を確認、実績値・証跡を残す。不一致が1つでもあればFail。 |
| 実施記録 | 実施日（日時・タイムゾーン）、担当者、Excel版（Windows/Web）・ビルド、保存先・権限、試験データセット/版、実績、証跡リンク、障害ID、状態、再試験結果を記載 |
| テスト時計 | 日付境界テストは `SystemToday` と `BaseDate` を分離。例示固定時計=2026-11-16（JST）は**入力フィクスチャ**であり、実時計が同日であることを要求しない。時計固定が不可能な場合は当日相対値で再設計し、同等性を記録する。 |
| テストデータ | 以下の案件A/B・E1等は**テスト用論理別名**であり、正式マスタコード/実PKを規定しない。実ID・コードは初期設定時に置換、`CFG-DD-10-01`未解決を維持。 |
| 実施順 | 基礎案件/適用 → 開催回/履歴/証跡 → 表示用抽出 → 独立フィルター/回復 → 環境/復元。前提未成立はBlockedとしPassにしない。 |
| 独立性 | 親と子の実施ケースを記録し、再利用したデータセット・共通証跡を参照できるが結果は個別に記録する。親の結果を子へ自動コピーしない。 |
| 分離 | 設計レビューでの **Case Designed** と実機の **Test Passed** は別概念。EXIT-DD-08の正式評価はExit Reviewでのみ行う。 |

**用語差の要確認**：REQ-MVP-002は管理適用の値を「対象／対象外／未判定」と書くが、DD12-01の出力表記は「管理対象／管理対象外／未判定」。本テストでは三状態の意味と保存・表示の一致を確認し、UI表記・内部コードの1対1対応は実装前に確定する（要件本文を黙って改訂しない）。

- `Blocked`／`Not Tested`の必須サブケースが1つでも残ればそのT15 IDをPassとしない。`N/A`は理由と承認が必要。
- OPS-DD11-01の誤登録訂正運用、CFG-DD-10-01、OI-DD-01/02、RISK-DD-01〜04は継続課題。詳細Exit／Gateを自動でMetにしない。
