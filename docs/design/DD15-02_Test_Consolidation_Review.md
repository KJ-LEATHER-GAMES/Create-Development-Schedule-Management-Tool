## 4. 採否に付随するテスト設計ルール

1. **詳細IDの実施状態は独立**：親のPassを子へ自動伝播しない。T15内サブケースは`Pass／Fail／Blocked／Not Tested／N/A（理由と承認）`を個別に記録。1つでも必須サブケース未合格ならT15全体をPassにしない。
2. **実機と模擬の区別**：隔離された試験ブックで障害注入手順を定義し、Excel Windows/Webおよび採用保存先で本番と同等の保証を立証する。ロジック模擬のみでは物理排他・原子的保存・復元がPassにならない。
3. **単一原本・権限制約**：運用対象の共有原本を破損させるための直接編集を行わない。試験用コピー、テスト環境、および追跡可能な隔離・故障注入を使用する。VBA/Office Scripts等の特定方式を新規必須としない。
4. **失敗時Fail-closed**：制約違反、競合、結果不明、部分保存、ID巻戻り、表示版不明では、その障害の**正本・表示の判定状態**を確認する。停止を黙って解除しない。
5. **復旧順**：R01〜R08を状態・根拠・版・高水位・期待行集合で照合。復旧不可時には`Blocked`を保持し、方式変更を正式変更管理へ上げる。
6. **テスト証跡**：入力データ、操作・障害注入、期待版／実測版、関連PK、OperationKey、発番高水位、実行日時（TZ）、OS/Excel版・ビルド、保存先、権限、観測結果、証跡リンク、障害IDを記録。
7. **採否と実施の分離**：A案の正式採用後も、全追加IDは`Not Tested`で開始する。現行31IDの原文・結果は不変。元C14/C15の22件は廃棄せず「T15へ統合」「既存に吸収」の**移行履歴**として残す。
