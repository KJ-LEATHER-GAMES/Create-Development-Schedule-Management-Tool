## 1. スコープ

### 対象
- 管理用マスタ／トランザクションデータの論理構造、主キー・関連の方針
- Excel管理画面：一覧編集、案件・イベントの詳細編集、要対応抽出
- 閲覧画面：4種類のガントチャート、今後2か月＋過去未開催イベント一覧
- 期間スライド、イベント重複時の集約、参照データと画面の分離
- 将来のQlik Senseでの再利用を妨げないデータ格納方針

### 対象外
- 調査票の設計・帳票フォーマット・回答回収・承認フロー
- 社内の判断基準自体の制定
- 外部システムからの自動取込、Qlik Sense実接続、通知、承認ワークフロー
- Excel数式・VBA・Power Queryの実装手法の確定（後続の詳細設計）

## 3. 提案アーキテクチャ（未承認）

```text
                 Excel単一ブック
 ┌─────────────────────────────────────────────┐
 │ ① 管理画面層                                │
 │  案件一覧・イベント一覧・詳細編集・要対応抽出│
 ├─────────────────────────────────────────────┤
 │ ② データ管理層                              │
 │  マスタ＋案件／適用要否／開催回／日程／資料  │
 │  不一致確認記録（必要最小限）                │
 ├─────────────────────────────────────────────┤
 │ ③ 表示用変換層                              │
 │  フィルタ、日付→旬、行集約、重複件数集計     │
 ├─────────────────────────────────────────────┤
 │ ④ 閲覧画面層                                │
 │  4種ガント、直近イベント一覧、単一機種画面  │
 └─────────────────────────────────────────────┘
                     │
           将来Qlik Senseへ表データを再利用
```

**設計原則（案）**：管理データの表を表示セルとして兼用しない。表示列の大量生成によって正本データが肥大化しないようにする。ExcelとQlik Senseは同じ構造化テーブルから必要な表示・分析を組み立てられるようにする。

## 4. 論理データ構造案（未承認）

| テーブル候補 | 1レコードの意味 | 主な項目案 | 関連 |
|---|---|---|---|
| `M_Model` | 1機種 | ModelID、機種コード、名称 | `T_Project`から参照 |
| `T_Project` | 1開発案件 | ProjectID、ModelID、案件番号、管理要否、管理属性 | 親レコード |
| `M_Stage` | 1開発ステージ | StageID、表示順、表示名 | マイルストーン・イベントから参照 |
| `M_EventType` | 1イベント種別 | EventTypeID、名称、表示順 | 適用要否・開催回から参照 |
| `T_EventApplicability` | 案件×イベント種別の適用判定 | ProjectID、EventTypeID、適用要否、根拠参照 | 原Q3の単位を維持 |
| `T_EventOccurrence` | 1イベント開催回 | OccurrenceID、ProjectID、EventTypeID、StageID（案）、回数／識別子、暫定日、確定日、実績日、状態 | 開催回単位で保存 |
| `M_MilestoneType` | 1開発マイルストーン種別 | MilestoneTypeID、名称、表示順 | 開発日程から参照 |
| `T_DevelopmentMilestone` | 案件に紐づく開発マイルストーン | MilestoneID、ProjectID、MilestoneTypeID、StageID（案）、正式日、暫定日、実績日 | 日付として保存 |
| `T_Document` | 1つの資料 | DocumentID、文書名称、種別、参照先、版 | 実ファイルは外部 |
| `T_DocumentRelation` | 資料と管理対象との関連1件 | RelationID、DocumentID、対象種別、対象ID、用途 | 1資料を複数対象へ紐づけ可能 |
| `T_Reconciliation` | 1つの不一致・照合記録 | CheckID、対象、確認日、対応状況、証跡 | OI-01 Q10に対応 |

**設計留意点**
- テーブル名、分割数、列名・ID型は案であり、確定したシート構成ではない。
- `T_EventApplicability`（イベントが必要か）と`T_EventOccurrence`（いつ何回実施したか）は別物である。対象イベントで開催回が未登録の場合に「未計画」と認識する方法は後続検討。
- 正式日程と暫定日程を混同しない。正本情報を速報で無条件に上書きしない。
- 資料関連付け先を複数種別にする方式は概念案。Excelの参照整合性検証方法は未決定。

## 6. ダッシュボード案（未承認の表示実装）

| 画面 | 表示行 | 期間粒度 | データソース |
|---|---|---|---|
| VIEW-01 開発日程一覧 | 1開発案件／行 | 上中下旬 | `T_DevelopmentMilestone` |
| VIEW-02 イベント一覧（日） | 開発案件×ステージ／行 | 1日 | `T_EventOccurrence` |
| VIEW-03 イベント一覧（旬） | 開発案件×ステージ／行 | 上中下旬 | `T_EventOccurrence` |
| VIEW-04 単一機種 | 対象機種内の案件・ステージ | 旬単位全体／日単位イベント切替 | 両方を統合 |
| 直近イベント一覧 | 1開催回／行 | 日付リスト | `T_EventOccurrence` |

表示ロジックは「フィルタ → 行キーの生成 → 期間バケット変換 → イベント数集計 → 重複の詳細参照」と分ける。イベントを同一日・旬へ集約しても、`OccurrenceID`単位の詳細にたどれることが必要。

### 開始位置スライド方式
- 日単位・旬単位とも表示列数は固定（確定方針）。
- 開始位置はユーザー入力により変更。表示範囲内にあるデータだけを表示する。
- 旬の区切り（上旬／中旬／下旬）、表示列数、移動単位は後続設計で確定。

## 8. 次の意思決定（BD-Q1）

**イベント開催回のステージをどの単位で管理するか**。

- **A**：イベント種別マスタにステージを固定し、すべての開催回に適用
- **B（推奨）**：開催回レコードにステージを保持する。案件／開催回ごとに異なるステージを設定可能
- **C**：イベント種別に標準ステージを設定し、開催回ごとに上書き可能

判断軸：案件×ステージのガント集約の整合性、更新時の運用負荷、同じイベント種別が異なるステージで生じる可能性。

Bを選んでも、既決の**イベント適用要否は案件×イベント種別で管理**するルールは変更しない。ステージをイベント適用要否まで拡張する必要性が判明した場合は、別途影響評価してから判断する。
