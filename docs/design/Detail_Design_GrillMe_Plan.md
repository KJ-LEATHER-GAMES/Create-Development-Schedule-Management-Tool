## 3. Objective

**既に確定した業務ルールを変更せず、Excel単一原本で主要User Casesを実装できるだけの最小限の詳細設計判断を、依存関係の強い順に確定する。**

特に、①案件・ステージ適用・イベント適用・開催回・日付履歴のレコード粒度と関連、②不変ID・参照ID・採番・参照整合性、③未計画と実効適用の導出、④代表日付・変更／訂正履歴の有効判定を優先する。必要な範囲でマイルストーン・証跡・照合・編集画面・ガント／一覧へのデータ接続を決め、実装担当者が迷わず着手できる判断記録を残す。

## 4. Scope

### 4.1 In Scope — 本GrillMeで判断すること

- **テーブル・粒度：** マスタと案件別データ、ステージ適用、イベント適用、開催回、マイルストーン、日付履歴、証跡、公式情報との照合差異の構成と関連。
- **ID・参照：** 主キー／外部キー、自然キーとの区別、採番と不変性、再開催時の新規ID、無効化・削除制限、重複・孤立行の防止方針。
- **状態・日付：** 未計画（適用対象かつ開催回なし）の導出、ステージ対象外時の実効対象外、開催状態、現行代表日付の選定、追記のみの訂正・変更、根拠追跡。
- **更新・表示への接続：** 管理者の一覧／詳細編集、要対応抽出、4ガント＋期限超過／開催予定の2一覧へ渡す最小項目と判定規則。
- **実装可能性への配慮：** Excel Windows／Web共通性、単一原本・管理者編集／閲覧専用、後続実装で確認する項目の記録、主要正常系の受入観点。
- **成果物：** 最小データ辞書、関連・不変条件、主要処理フロー、仕様判断、決定事項と未決事項の対応表を後続 `MVP_Design` へ統合するための確定材料。

### 4.2 Out of Scope — 本GrillMeで決めない・実施しないこと

- 調査票、新規承認ワークフロー、社内の正式承認制度改正。
- Qlik Sense実接続、外部自動同期、通知機能、開催後の宿題・指摘対応進捗管理。
- 全案件の本番データ投入、Excelブックの実装、Box／SharePointでの事前PoC、環境・性能・復元の実機試験。
- 無条件のVBA必須化やOffice Scripts必須化、追加の定期別バックアップ、網羅的な異常系・境界値テストの前倒し。
- 確定済みの基本設計Q1〜Q33、条件付き移行Gateの再採決。

## 9. 最初に検討するテーブル・ID論点

### 9.1 確定している論理モデル（再質問しない）

```text
開発案件（機種×案件で識別）
 └─ 案件別ステージ適用（案件登録時に標準ステージ分を生成）
     └─ 案件別イベント適用（ステージ対象時に初めて生成）
         └─ 開催回（開催計画時に初めて生成、再開催は別開催回）
             └─ 日付変更・訂正の追記履歴

ステージマスタ ──< イベント種別マスタ（所属ステージ固定）
開発案件 ──< 開発マイルストーン ──< 日付履歴（粒度・共通化は未決）
案件・開催回等 ──< 証跡リンク、照合差異（紐付け設計は未決）
```

この図の**業務上の上下関係と生成時点は確定**。テーブル名・主キー・外部キー・履歴構造そのものは**未決**である。

### 9.2 物理テーブル候補（未承認、Q01以降で選定）

| 候補 | 1行の意味（粒度） | ID／参照の主要論点 |
|---|---|---|
| `tblProject` | 1開発案件 | 内部ProjectIDと外部公式案件識別子を分離するか |
| `mstStage` | 1標準ステージ | StageIDの固定値・改廃 |
| `mstEventType` | 1イベント種別 | EventTypeID、所属StageID（固定） |
| `tblProjectStage` | 1案件×1標準ステージの適用判定 | ProjectStageID、ProjectID、StageID、重複不可 |
| `tblProjectEvent` | 1案件×1イベント種別の適用判定 | ProjectEventID、所属ステージとの整合、過去判定の保持 |
| `tblOccurrence` | 1開催計画／再開催回 | OccurrenceID、ProjectEventID、回次／状態 |
| `tblDateHistory` | 1日付変更・訂正の追記レコード | HistoryID、対象ID、現行有効レコード選択方式 |
| `tblMilestone` | 1案件×1マイルストーン実体 | MilestoneID、案件ID、正式情報との参照 |
| `tblEvidence` | 1証跡／成果物の参照レコード | EvidenceID、案件／開催回等への紐付け |
| `tblReconciliation` | 1不一致・確認記録 | ReconciliationID、対象IDと解消記録 |

**テーブル数・名称は設計候補であり確定ではない。** `tblDateHistory` を開催回とマイルストーンで共通にするか、別テーブルにするか（Q09）は未決。Excelの表示／計算補助テーブルは実装に必要な場合に限り決め、無条件には増やさない。

### 9.3 ID管理で最初に固定すべき不変条件（制約候補）

1. **再開催と日付変更を識別できること。** 同じイベントでも再開催は別OccurrenceID、同一開催回の予定日変更は同OccurrenceIDへ履歴追加。
2. **未計画の架空開催回を作らないこと。** 適用対象かつ開催回ゼロから管理画面側に未計画を表現する。
3. **適用対象外化しても過去の判定と履歴を消さないこと。** 参照上の実効値は変えても保存値は保持。
4. **履歴は追記専用。** 誤記訂正は元HistoryIDを残して新HistoryIDを追加。
5. **代表日付の同時二重化を防ぐこと。** どの履歴が現行有効か一意に求める。ただし判定アルゴリズムはQ10/Q11で決定。
6. **Excel画面上の行番号を永続IDにしないこと。** 行の挿入・並べ替え・フィルターで参照先が変わるため、これは設計上の推奨制約として提案する（未承認）。
7. **重複キー・孤立参照を検出できること。** 検出方法と入力防止／修正手順はQ06/Q08で決定。

### 9.4 先行判断の依存関係

`Q01 行粒度・テーブル分割` → `Q02 主キー方針` → `Q04/Q05 親子参照` → `Q06 ID採番` → `Q07 開催回識別` → `Q09〜Q11 履歴の有効判定` → `Q15 未計画導出` → `Q19〜Q22 編集・表示`。

IDの付け方を先に確定する前に、**何を1レコードとして識別するのか**をQ01で固定する。後で同一イベントの再開催／日付変更を誤って同一レコードに畳み込む設計を避けるため。

## 10. Q01 — 最初のGrillMe質問（回答待ち）

**質問：案件別イベント適用を、Excelの物理データ上でどの単位のテーブルとして保持しますか？**

いずれも「ステージとイベント種別の所属はマスタ固定」「未計画に開催回を作らない」という既決条件を保持する。これは**既存の論理階層を変更する質問ではない**。

| 選択 | 構成 | 利点 | 主なトレードオフ |
|---|---|---|---|
| **A（AI推奨）** | 案件、案件別ステージ適用、案件別イベント適用、開催回を**別々のテーブル**にする（マスタ・日付履歴も独立） | 1行の意味が明確。未計画・再開催・保存判定の独立性、履歴・Qlik拡張の追跡が容易 | Excel表が増え、キーの参照・整合性チェックが必要 |
| B | ステージ適用行とイベント適用行を**種別列つきの同一適用テーブル**で保持し、開催回は別表 | 適用判定テーブル数が少ない | 行によって必須列と参照先が異なり、式と入力規則が複雑化 |
| C | 案件×ステージ適用は別表、イベント適用はその行に**イベント種別ごとの列**を持たせ、開催回は別表 | 少数のイベント種別なら管理表が横に見やすい | イベント種別追加時に列変更が必要。1イベント1レコードでの履歴・参照が難しい |

**AI推奨：A。** 適用判定と開催回を別の実体として扱えるため、開催回ゼロの未計画、既存判定を残した実効対象外、再開催に対して整合性を説明しやすい。テーブル増加はあるが、MVPで既に必要とされている情報単位に限定する。

**回答形式：** `詳細設計GrillMe Q01はAで進めます。` など。選択された時点で初めてQ01を確定扱いし、次のQ02へ進む。
