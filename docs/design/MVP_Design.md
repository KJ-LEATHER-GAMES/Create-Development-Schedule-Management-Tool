## 1. 目的・境界・参照順

### 1.1 目的と利用者

機種×開発案件を起点に、案件の管理適用、ステージ／イベント適用、開催回、マイルストーン、Excel内の日付履歴、証跡、公式情報との差異を管理者が更新し、関係者が **4ガント＋期限超過／開催予定の2一覧**を閲覧できるMVPの**実装判断に必要な最小設計**を示す。管理担当者が原本を原則1名で編集し、機種開発責任者が適用判定の最終判断者となる。閲覧者は原本管理値を変更しない。

### 1.2 In Scope／制約

- **[確定判断]** Excel単一原本、Excel Windows版／Web版対象、Box第一候補・SharePoint Online代替。保存先未決定、技術的成立性未検証。
- **[確定判断]** 案件→ステージ→イベント種別（所属StageIDはマスタ固定）、開催回は計画時生成。再開催は別回。マイルストーン・証跡・外部差異もMVP内。
- **[確定判断]** 共通表示データからガント4画面と直近イベント2一覧を構成。閲覧者別・画面別の独立絞り込みが必須。ガントの表示開始期間は管理担当者のみ変更可能。
- **[確定判断]** 実機PoCは先行させず、実装と並行して環境・性能・採番等の成立性検証を行う。追加の定期別バックアップは設けずクラウド版履歴を使う方針（保持・復元条件は未確認）。VBAまたはOffice Scriptsを必須化しない。
- **[Not Now]** 調査票、新規承認WF、組織制度改正、事後宿題管理、Qlik Sense実接続、外部自動取込・通知、全件実データ投入、網羅的な事前テストは追加しない。

### 3.2 採用する現在の仕様（承認済み変更部分）

1. 案件登録時に`tblProject`を登録し、全標準ステージについて`tblProjectStage`を**未判定**で生成する。
2. **同じ案件登録処理で、登録時点の全イベント種別について`tblProjectEvent`を未判定で生成**する。所属StageIDはイベント種別マスタで固定し、案件×イベント種別の重複を禁止する。
3. ステージが`対象`・`対象外`・`未判定`に変更されても、**イベント適用行を新規生成・削除しない**。保存済み判定を保持し、実効判定は親ステージ×イベント判定から都度算出する。
4. **適用行の存在は開催計画の成立を意味しない**。`tblOccurrence`は開催計画時のみ生成し、非適用化しても既存開催回と日付履歴を削除・自動中止しない。
5. 登録後にイベント種別マスタが追加された場合、管理者の**明示的な差分同期（Q08）**で既存案件に不足分だけ生成する。追加したイベント行も未判定で開始し、既存行と判定を保持する。

### 3.3 未解決事項・承認の限界

- **初期行数増加**：件数の概念値は案件数×登録時点のイベント種別数。想定規模・Excel性能は未検証（**OI-DD-01／基本設計EXIT-06 Not Met**）。
- **登録処理の原子性と採番競合**：**OPN-DD-14**（方式未確定、実機検証なし）。
- **マスタ同期の部分失敗・復旧**：**OPN-DD-15**。親が未判定・対象外の際の表示・抽出明細：**OPN-DD-12**。

## 4. 論理構成・データ辞書

### 4.1 アーキテクチャ（処理概念、物理実現は未選定）

```text

       (StageID一致が条件)         └─EventTypeID  └── tblDateHistory[Occurrence]

Evidence / Reconciliation ── 対象種別＋対象ID（紐付け対象とルールはDraft案）
```

- **[確定判断]** 主要PKは不変、発番済みIDは再利用しない。参照不能・重複の状態では保存を拒否する。イベント種別の所属ステージを案件別に勝手に変更しない。
- **[Draft補完案]** 案件別イベント適用行は同一案件の`tblProjectStage`にリンクし、EventTypeが持つStageIDと一致することを保存前に検証する。複合UQは業務上の二重生成を防ぐ。
- **[確定判断]** 開催回の日付変更は既存`OccurrenceID`に履歴を追加し、再開催は**新`OccurrenceID`と新`OccurrenceNo`**を採番する。開催回の削除・置換で再開催を表現しない。
- **[Draft補完案]** 親参照先が既存履歴・開催回・証跡から参照される場合は物理削除せず有効区分等で管理する。廃止・削除の正確な方針はExitまでにレビューする。

## 5. ID採番・生成・同期・整合性

### 5.1 テーブル別連番（Q06、Q11、Q18）

**[確定判断]** IDは主要テーブルごとに独立した連番で、不変・再利用不可・重複不可。`HistoryID`の比較順が同一対象の**正常確定順**と矛盾してはならない。イベント別`OccurrenceNo`は`ProjectEventID`内で連番とし、再開催ごとに別回を作る。

**[Draft補完案：不変条件]**

1. 発番は登録／追記の**確定処理**と不可分に扱う。欠番は許容しても、過去IDの再利用はしない。
2. 同じテーブルに同一PKが2件ない。異なる端末が同時に採番しても同一PKを確定させない。
3. `HistoryID`が大きい正常確定レコードが、同一対象の確定時系列でより新しいことを保証する。単に複数端末で`MAX()+1`を計算するだけでは保証しない。
4. 登録失敗・通信切断・再試行で同一要求が二重登録されないことを検証する。実現方式が未定なら**自動採番の成立を宣言しない**。
5. 連番管理をどのExcel機構で安全に行うか、複数端末の排他・再送、同時編集の許容有無、操作権限は**OPN-DD-14（Now）／RISK-DD-04（Later実機検証）**。

### 5.2 案件登録とイベント適用行の生成（CONS-DD-01 A承認）

1. 管理者が機種・案件・外部公式識別情報を入力し、既存の機種×案件と照合（重複時は保存拒否）。
2. `tblProject`の不変`ProjectID`を確定し、全標準ステージについて`tblProjectStage`を`未判定`で生成（**Q04確定**）。
3. **イベント適用行生成（CONS-DD-01 A承認）**：同じ登録処理で、**その時点の全イベント種別**について`tblProjectEvent`を`未判定`で生成する。各`ProjectEventID`は不変、UQ(`ProjectID`,`EventTypeID`)で二重生成を禁止。親ステージが`未判定`でもイベント適用行は生成するが、実効対象として扱わない。
4. 親子FK・UQ・初期判定・**登録時点の全ステージ／全イベント種別の生成件数**を一括検証し、不整合な**登録を正常確定させない**。失敗時の原子性と復旧方式は**OPN-DD-14**。
5. 作成された適用判定は管理者操作で更新し、機種開発責任者の最終判断を業務上の根拠とする。ステージが`対象`へ変わっても**イベント適用行を再生成しない**。`対象外`／`未判定`への変更でも既存判定を消さない。判定値が`未判定`の間も**開催回を機械的に生成しない**。

### 5.3 マスタ差分同期（Q08）

管理者が明示実行するまで、**登録後に追加されたマスタを既存案件へ自動反映しない**。実行時は新規StageID／EventTypeIDと既存案件別行の差分を検出し、**追加ステージについて全既存案件に未判定のステージ行を、追加イベント種別について全既存案件に未判定のイベント行を不足分だけ生成**する（所属ステージ参照の整合を検証）。ステージが`対象`となった時点ではイベント行を生成しない。既存の`ProjectStageID`／`ProjectEventID`と判定値、開催回・履歴は保持。同期処理失敗時は「未完了／要確認」を表示し、再実行時にUQによる二重追加を防止する。**差分の再実行・部分失敗の扱いはOPN-DD-15（Now）**。

### 5.4 保存前／全体整合性検証（Q07）

| 検証レベル | 最小チェック（Draft仕様案） | 失敗時 |
|---|---|---|
| 入力 | 必須列、適用値・開催状態・日付区分、参照リンク形式 | エラー理由と対象行を返し保存しない |
| PK／UQ | ID重複、案件×ステージ、案件×イベント、イベント別回次の重複 | 正本登録拒否、既存行不変 |
| FK | 存在しない案件／ステージ／イベント種別／開催回、所属Stage不一致 | 正本登録拒否 |
| 履歴 | 対象種別・対象ID不整合、日付・取消ルール、正常確定・HistoryID順 | 正常確定拒否、エラー表示 |
| 全体 | 既存孤立行、二重行、最新履歴の選定不整合、表示鮮度 | データ不整合は管理者へ要修正として明示。保存できない範囲・修復手順は要設計 |

## 6. 代表日付・共通履歴

### 6.1 正本の範囲（CONS-DD-03）

**[確定判断]** `tblDateHistory`は**Excel内の開催回・開発マイルストーンの現行代表日付**を導出するための唯一の正本。`tblOccurrence`／`tblMilestone`の代表日付表示列やガント用日付列は**派生値・キャッシュ**であり、履歴と独立して更新しない。一方、部品表システムの公式日程、開催通知、議事録など**外部の業務正本を置換するものではない**。公式情報との差異は§10の照合情報で扱う。

### 6.2 履歴追記と代表日付導出（Q09〜Q14）

**[確定判断]** 対象キーは`(TargetType,TargetID)`、日付の設定・変更・訂正・取消は**新しいHistoryID行を追記**する。変更前日付は過去履歴から導出し、元行を書き換えない。変更種別、変更後日付、理由、記録者、記録日時等を確認し、種別ごとに入力を検証する。

```text
代表日付を求める論理手順（Q11・Q13の確定部分）
  1. 対象種別と対象IDが一致する履歴を取得
  2. 「正常確定」した行だけに絞る
  3. HistoryID（テーブル別連番）が最大の行を選定
  4. その行が「取消」なら代表日付＝空欄（過去日の復活はしない）
     それ以外は選定行のAfterDateを代表日付として採用
  5. DateClass（暫定／正式／実績）と履歴IDを表示用派生値として供給
  ※履歴なし：代表日付未設定。無効な行がある場合は検証エラーを通知する
```

| 操作 | 履歴操作 | 現行代表日付の結果 | 設計上の注記 |
|---|---|---|---|
| 初回設定 | 正常確定の新行を追加 | 新しい日付 | `DateClass`を保持 |
| 予定変更 | 新行に変更後日付・理由を記録 | 新しい日付 | 旧日付は先行履歴から導出 |
| 誤入力訂正 | 正しい日付で新行を追加 | 訂正日付 | 誤入力行も保持 |
| 設定取消 | `AfterDate`空欄の取消行を追加 | **空欄** | 過去有効日の復活は禁止 |
| 取消後の再設定 | **新行を追記する方針案** | 新しい日付 | `ChangeType`・必須条件は**OPN-DD-11** |
| 履歴が存在しない | 追加なし | 空欄（未設定） | 未計画とイコールではない（未計画は開催回なし） |

**[Now／OPN-DD-11、OPN-DD-14]** 「正常確定」の機械判定（確定状態列・確定処理完了順・操作中断時の扱い）、取消行の`DateClass`、取消後の再設定の変更種別、日付・開催状態の同時操作は、確定判断に抵触せず実装前に定義する。`RecordedAt`ではなく**HistoryID最大**で代表を選ぶ判断は変更しない。

### 6.3 正式／暫定／実績

**[確定判断]** 代表日付は同時に1つ。正式／暫定／実績を別々の現行値として並立表示しない。区分は代表履歴に紐付く属性として保持し、ガントでは既決の視覚スタイルを使う（色・凡例の具体値はDraft補完課題）。日付超過をもってイベントを開催済に自動変更しない。

## 7. 適用状態・イベント状態・再開催

### 7.1 実効適用と未計画（Q15、CONS-DD-02）

**[確定判断]** ステージ判定が`対象外`となっても、イベントに保存された判定値は上書きせず、イベントの実効適用状態を参照時に都度算出する。実効値そのものを正本テーブルへ重複保存しない。

| 親ステージ判定 | 保存済みイベント判定 | 実効イベント判定（Draftとしての明文化） |
|---|---|---|
| 対象外 | 対象／対象外／未判定 | **対象外**（保存値は維持） |
| 未判定 | 対象／対象外／未判定 | **未判定**（親未決を優先する案。**行は存在**） |
| 対象 | 対象 | **対象** |
| 対象 | 対象外 | **対象外** |
| 対象 | 未判定 | **未判定** |
| 対象／未判定／対象外 | 未作成（同期待ち・異常を含む） | **正常な新規案件では発生しない**。登録後の新マスタ未同期、またはデータ不整合を検出・管理者へ通知（原因別の表示・阻止はOPN-DD-12／15） |

**[CONS-DD-01承認に伴う表示上の不変条件]** `tblProjectEvent`行の存在を実効`対象`や「開催回あり」と誤判定しない。親が未判定／対象外の場合は§7.1で実効判定を求め、閲覧向け開催予定・期限超過への混入を防ぐ（正確な例外包含条件はOPN-DD-12）。

**[確定判断＋粒度の整理]** `未計画`は**実効適用＝対象のイベントで開催回が1件もない**状態を導出する（架空開催回を作らない）。要件の4状態「未計画／計画済／開催済／中止」は業務表示上保持。開催回の記録状態は別粒度で「開催予定／開催済／中止」。**Draft表示マッピング**として「開催回なし＝未計画」「開催回あり＋開催予定＝計画済」を対応付ける。ただし**複数開催回が異なる状態のときイベント単位で何を代表表示するかはOPN-DD-11**で確定し、勝手に過去回を潰さない。

### 7.2 開催回の状態・遷移（Q16、Q17、Q18）

**[確定判断]** `OccurrenceStatus`を各開催回へ保存し、許可された遷移以外は拒否。開催済＝会議開催の事実であり、事後宿題完了ではない。非適用化しても過去開催回・日付履歴を保持し**自動中止しない**。再開催は新開催回として別`OccurrenceID`を発行し、疑似重複を警告・確認する。

| 遷移（Draftの原則案） | 扱い | 確定／未決 |
|---|---|---|
| 新規開催計画 → 開催予定 | 新`OccurrenceID`と`OccurrenceNo`を付与 | **計画時生成は確定**。初期値・実装はDraft |
| 開催予定 → 開催済 | 議事録・実施記録等に基づき管理者が明示操作 | **自動開催済にしないことは確定**。証跡必須条件はNow |
| 開催予定 → 中止 | 管理者が中止理由と根拠を入力する案 | **例外遷移・必須項目はOPN-DD-11** |
| 開催済／中止 → 他状態 | **自動で許可しない。例外・訂正経路は未定義** | **OPN-DD-11** |
| 実効適用が対象外になった既存回 | 消去せず履歴参照は可能。警告を表示し変更操作を制限 | 制限操作の明細は**OPN-DD-11** |
| 同じイベント・同一日で回を追加 | 既存開催回の重複疑いを警告し、確認を要求 | 重複検出の定義は**OPN-DD-11／14** |

注意：この遷移表は未決の例外経路まで許可したものではない。正式な許可／禁止一覧・エラーコード・取消と状態の連動は詳細設計Exitまでに定義する。

### 8.2 保存・表示更新シーケンス（Q20〜Q22）

```text
管理者操作
  → 入力・参照・重複・状態遷移の検証
    → エラー：正本を未確定／未変更として理由を表示
    → 正常：正本保存を確定
       → 共通表示データ再生成を自動実行
          → 成功：更新状態=正常、最終正常更新日時を記録、画面へ反映
          → 失敗：正本保存は取り消さない

```

**[Draft補完案]** `DisplayRefreshStatus`（正常／更新中／失敗／未生成）、`LastSuccessfulRefreshAt`、`LastRefreshError`、`SourceRevision`／`DisplayRevision`のような**表示鮮度の判定材料**を管理する。これらの物理格納先や復旧手順は**OPN-DD-15**。正常表示と断定できない場合は閲覧画面にも**古いデータの可能性**を明示する。

### 8.3 差分同期・更新失敗時の再実行

保存成功と表示成功は別の結果として扱う。正本更新が成功し表示更新に失敗した場合、正本から共通表示データだけを再生成し、元の更新を二重登録しない。マスタ同期が部分失敗した場合に不変ID／判定値を破壊せず再実行できる条件、各失敗の原子性・復旧レベルは**[Now] OPN-DD-15**。データの破損・孤立が判明しているときは更新状態を正常に偽装しない。
